## 1. 技术结论

本项目的应用层技术可行：本地消息存储、全文搜索、语义检索、摘要、画像、知识卡和 Obsidian 导出均可使用成熟技术实现。

主要不确定性集中在个人微信数据采集层。个人微信没有面向普通第三方的稳定全量历史 API；现有方案通过读取用户本人电脑端微信已经同步到本机的数据实现。`sjzar/chatlog` 已因微信官方函件移除代码，因此不得作为当前依赖。`jackwener/wx-cli` 可作为 Windows 本机 PoC 的研究参照，但采集层必须保持可替换，且在许可和合规验证通过前不得承诺对外商用。

参考：

- chatlog 移除说明：https://github.com/sjzar/chatlog
- wx-cli 当前仓库：https://github.com/jackwener/wx-cli
- WorkBuddy 微信助理说明：https://www.codebuddy.cn/docs/workbuddy/WeixinBot-Guide
- Hermes iLink Bot 说明：https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/messaging/weixin.md

WorkBuddy/Hermes 属于“微信作为 Agent 入口”，不能替代历史会话采集。它们可在未来作为“从微信查询记忆库、接收摘要”的交互入口。

## 3. 技术栈

| 层级 | MVP 选择 | 说明 |
| --- | --- | --- |
| 本地采集适配器 | Rust 独立二进制 | 负责 Windows 本地数据读取、分片发现、新鲜度和标准化；PoC 先验证现有工具能力 |
| 本机通信 | Windows Named Pipe 或仅监听 `127.0.0.1` 的本地接口 | 禁止绑定公网地址；接口返回标准化模型，不泄露底层密钥 |
| 应用后端 | Python 3.11、FastAPI、Pydantic、SQLAlchemy | AI 生态成熟，适合业务编排与本地 API |
| 原始数据 | SQLite，生产包可评估 SQLCipher | 单用户本地应用足够；开启 WAL、外键和定期完整性检查 |
| 全文搜索 | SQLite FTS5 | 第一优先级，保证 AI 不可用时仍能搜索 |
| 语义搜索 | Ollama + BGE-M3 | 默认本地 embedding；按对话块而非每条碎片消息建立语义索引 |
| 向量存储 | MVP 采用嵌入式方案，达到规模阈值后评估 Qdrant | 不在 PoC 阶段提前引入独立服务 |
| 后台任务 | APScheduler 或轻量本地任务队列 | 负责 5 分钟同步、22:00 整理和失败重试 |
| 前端 | React、TypeScript、Vite | 桌面工作台 UI |
| 组件与图标 | Ant Design 或经 UI 方向确认后的组件体系 | 最终选择由视觉稿决定 |
| 桌面封装 | Phase 1 后评估 Tauri | 先以本地 Web UI 验证业务闭环，再封装安装包 |
| 测试 | Pytest、Vitest、Playwright（获得用户同意后） | 单元、集成、E2E 分层验证 |

## 4. 采集适配器契约

采集适配器只承担以下职责：

1. 检测当前 Windows 用户下的电脑版微信运行与账号状态。
2. 发现本地会话、消息、联系人、群成员及资源索引的数据分片。
3. 返回指定水位后的新增记录，并提供源库最新时间、未知分片和可能滞后状态。
4. 把微信内部格式转换为版本稳定的标准消息模型。
5. 保持只读；不发送消息、不修改微信数据、不代替用户登录。

禁止把以下能力放入适配器：

- 客户画像、AI 摘要、向量索引或 Obsidian 导出。
- 用户业务数据库的写入逻辑。
- 任何云端上传逻辑。
- 自动回复、群发、加好友或营销操作。

建议适配器返回统一状态：

| 状态 | 用户含义 | 应用行为 |
| --- | --- | --- |
| `ready` | 当前数据可读 | 允许首次或增量同步 |
| `wechat_offline` | 电脑版微信未运行 | 暂停并等待用户登录 |
| `unsupported_version` | 当前微信版本不兼容 | 保留既有数据，停止新增读取 |
| `possibly_stale` | 源数据可能领先于已读数据 | 扩大回读并提示用户 |
| `unknown_shards` | 存在未纳入的分片 | 不得宣称同步完整，要求重新初始化 |
| `account_changed` | 检测到不同微信账号 | 隔离账号空间，禁止合并 |
| `permission_denied` | 当前进程权限不足 | 展示最小化恢复说明 |

## 5. 标准消息模型

业务层不得依赖微信数据库原始字段名。标准模型至少包括：

```text
Message
├── source_account_id       来源账号稳定标识
├── source_shard_id         来源分片标识
├── source_message_id       来源消息标识
├── conversation_id         会话稳定标识
├── conversation_type       private / group / official / other
├── sender_id               发送人稳定标识
├── sender_display_name     当时可见名称
├── sent_at                 消息时间
├── direction               incoming / outgoing
├── message_type            text / image / voice / video / file / link / system / unknown
├── text_content            可读正文
├── structured_content      引用、链接、文件等结构化信息
├── attachment_metadata     文件名、大小、哈希、可用位置等
├── raw_payload             必要的原始载荷，受控保存
├── source_freshness        来源新鲜度
└── ingested_at             入库时间
```

业务消息主键建议由账号、分片和源消息标识组成；若源标识不稳定，则增加时间、会话和内容指纹形成复合去重键。任何哈希只用于本地去重与完整性，不上传外部服务。

## 6. 首次归档流程

1. 完成账号、版本、目录和权限检测。
2. 建立当前账号独立的数据空间。
3. 扫描全部已发现分片，生成覆盖范围预览。
4. 用户确认范围后，以只读快照方式分批读取，避免与微信写入冲突。
5. 标准化并批量写入 SQLite；通过唯一约束保证重复运行幂等。
6. 每批提交检查点，支持崩溃或退出后恢复。
7. 原始消息入库后先建立 FTS5，尽快开放基础搜索。
8. 后台生成对话块与 embedding，不阻塞基础搜索。
9. 对比源库最新时间、已读时间和分片清单，生成覆盖报告。
10. 只有完整性检查通过才显示“归档完成”；否则显示“需关注”。

## 7. 增量同步流程

### 7.1 触发策略

- 应用启动：立即触发补同步。
- 应用运行：默认每 5 分钟触发一次。
- 用户操作：支持“立即同步”。
- 文件变化通知：可作为加速信号，但不能作为唯一触发源，避免漏事件。

### 7.2 一次增量任务

```text
获取互斥锁
  → 检查账号与兼容性
  → 发现新增或变化分片
  → 读取每个分片的同步水位
  → 从水位之前的重叠窗口开始回读
  → 标准化并按唯一键去重
  → 事务写入原始消息
  → 更新分片水位与完整性状态
  → 提交全文索引更新任务
  → 提交语义和AI派生任务
  → 更新用户可见状态
  → 释放锁
```

同一账号同一时间只允许一个同步任务。重复触发应合并，不并发读取和写入。

### 7.3 失败恢复

- 单个分片失败不得推进该分片水位。
- 原始消息事务提交成功后，索引失败可单独重试。
- AI任务失败不得回滚原始消息。
- 应用崩溃后根据检查点和唯一键恢复。
- 微信退出时不持续高频重试；进入低频检测，用户重新登录后立即补同步。

## 8. 搜索设计

搜索分三层：

1. **结构化过滤**：账号、联系人、群、时间、消息类型、文件名。
2. **全文检索**：原文、引用文本、链接标题、文件名和可用 OCR/转写文本。
3. **语义检索**：将连续对话按会话和时间窗口切块，避免单条“好的”“收到”污染向量空间。

混合排序需保留可解释性：展示命中的原词、语义相关原因、时间和来源。AI答案不能替代搜索结果列表；无证据时必须回答“没有找到足够依据”。

## 9. AI 派生数据

AI 生成内容统一视为“派生数据”，不得覆盖原始消息。

| 类型 | 主要字段 | 必须关联 |
| --- | --- | --- |
| 每日摘要 | 重点、变化、风险、可忽略项 | 原始消息集合 |
| 待办建议 | 内容、候选责任人、候选截止时间、状态 | 至少一条来源；不确定字段标为待确认 |
| 联系人事实 | 公司、角色、需求、顾虑、承诺 | 逐事实来源、置信状态、用户锁定状态 |
| 决策卡 | 决策内容、参与人、时间、影响 | 决策原话及前后文 |
| 知识卡 | 类型、标题、摘要、标签、双向链接 | 支撑消息和用户编辑历史 |

用户确认过或锁定的内容优先级高于 AI 新建议。发生冲突时创建变更建议，不静默覆盖。

## 10. 数据库模块

建议业务表：

- `accounts`：本地微信账号隔离。
- `conversations`：私聊、群聊、公众号等会话。
- `contacts`：联系人稳定身份和当前显示信息；至少包含 `account_id`、源端稳定标识、备注名、微信昵称、用户确认实名、当前头像资源引用、头像版本/更新时间。身份匹配不得依赖昵称、实名或头像。
- `contact_avatar_cache`：微信头像本地缓存元数据；新版本成功校验后原子切换当前引用，旧版本按缓存策略清理。无头像时由前端按显示名生成首字占位，不写入伪造图片。
- `messages`：标准化原始消息。
- `attachments`：附件元数据和本地归档状态。
- `sync_shards`：各源分片水位、新鲜度与错误状态。
- `sync_runs`：每次同步任务的开始、结束、数量和结果。
- `search_chunks`：语义检索对话块。
- `facts`：联系人或项目事实、来源、审核和锁定状态。
- `summaries`：每日摘要及生成状态。
- `action_items`：待办建议和用户确认状态。
- `knowledge_cards`：知识卡与导出状态。
- `source_links`：所有派生内容到原始消息的多对多关系。
- `export_manifests`：Obsidian 导出清单、冲突和版本。

所有表按账号隔离。原始消息表只允许追加或显式删除；AI重新生成只修改派生表。

## 11. 本地安全要求

- 应用与采集器只以当前 Windows 用户身份运行。
- 本地接口仅允许当前用户访问；不得监听局域网或公网。
- 不在日志中输出聊天原文、密钥、数据库路径中的账号标识或云端凭证。
- 解密过程产生的临时副本必须限制访问、记录生命周期并在安全条件下清理。
- 云端 AI 默认关闭；开启时按任务展示出站范围并获得确认。
- 备份文件支持用户选择加密；恢复前验证完整性和版本。
- 删除账号数据与清理索引必须二次确认并生成可理解的结果报告。

## 13. 开发阶段与退出条件

### Phase 0：采集 PoC

目标：证明当前用户 Windows 环境下能只读、稳定地获得可用数据。

验收：

- 检测当前账号和微信版本。
- 从 3 个私聊、3 个群读取文本、时间、发送人和会话。
- 验证文件名、链接、引用、语音与图片元数据的覆盖率。
- 连续运行至少 24 小时，验证 5 分钟增量、关闭后补拉和去重。
- 输出完整性状态，不把“读到部分数据”误报为完整。
- 记录许可和合规结论；未通过时停止商业化路线，但可继续应用层模拟数据开发。

### Phase 1：消息库与全文搜索

退出条件：

- 首次归档可恢复、可去重。
- 启动补同步和周期同步稳定。
- FTS5 支持人、群、时间、文件名和原文检索。
- 原文上下文与同步状态可在 UI 查看。

### Phase 2：语义搜索与今日整理

退出条件：

- 混合检索可降级，不依赖 AI 才能使用。
- 22:00 定时任务可补做、可追溯。
- 摘要和待办逐条关联来源。

### Phase 3：画像、知识卡与 Obsidian

退出条件：

- 画像事实支持接受、编辑、锁定和冲突提示。
- 知识卡重复导出不覆盖用户自由编辑内容。
- 删除源消息后派生内容显示来源失效状态。

### Phase 4：桌面封装与发布准备

退出条件：

- Windows 安装、升级、卸载与数据保留策略明确。
- 完成大数据量、断电恢复、权限、日志脱敏和本地接口安全测试。
- 产品文案不承诺手机端全量、零遗漏或永久兼容。
